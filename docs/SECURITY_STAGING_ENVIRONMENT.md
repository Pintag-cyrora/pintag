# Isolated staging environment for credentialed security tests — design (not yet built)

**Status: design only. No staging project exists, none is listed in `tests/security/staging-targets.txt`, and therefore every credentialed security test is disabled.**
The existing `Pintag-dev` project is **not** to be used: its seed history and contents are unverified (it may contain data copied from production).

## Why
The live security suite probes production anonymously and read-only (see `tests/security/README.md`). Some controls can only be proved with credentials or with a
successful write: administrator access with MFA (AAL2), cross-user isolation, storage upload rules, the end-to-end insert and deduplication paths, XSS payload storage.
Those must run somewhere a mistake or a failed cleanup harms nothing.

## Requirements for the project (all must hold before its reference is listed)
1. **Dedicated**: created only for testing; never the production project; never a project that ever received a copy of production data (no dump, no restore, no seed script that reads production).
2. **Synthetic data only**: invented names, phone numbers, addresses, coordinates and listing identifiers; nothing derived from a real record.
3. **Separate credentials**: its own anon key, service key, administrator and test users. No credential is shared with production or the development project.
4. **Production-equivalent authentication**: the single-administrator allowlist and the TOTP / AAL2 requirement behave exactly as in production, so the O3 matrix (non-admin, administrator at AAL1, administrator with MFA) is exercised for real. A test that needs an AAL2 session obtains it through the same TOTP flow, with a test-only authenticator secret held only in the staging secret store.
5. **Same schema**: all migrations applied in the same order as production, verified by a drift check before each run.
6. **Isolated side effects**: no production storage buckets, no production Edge Function secrets, no outbound notification channel; AI-provider keys, if any, are separate and rate-limited.
7. **Disposable**: documented procedure to reset it to its synthetic baseline.

## How the suite uses it
* The reference is added to `tests/security/staging-targets.txt` in a reviewed pull request, and the run sets `SECURITY_TARGET_CONFIRM=<same reference>`.
* The target is classified from the project reference in `SUPABASE_URL` (`tests/security/lib/target-guard.sh`), never from `APP_ENV`. A listed reference can never be the production reference.
* A separate workflow job (not the production job) receives the staging secrets. The production job never receives administrator or test-user credentials.
* Cleanup in staging is tracked and verified: ids are generated by the test and registered before the request, rows carry a `pentest-<run>` marker, a failed delete fails the run, a read-back by marker must be empty, and a sweep at the start of each run removes rows left by a crashed run.

## What is NOT claimed
Until this environment exists: administrator, cross-user, storage-write, and XSS-payload tests are not run anywhere; AAL1 refusal and MFA enforcement rest on migration code and catalog checks (see the O3 status in the security evidence record, pull request #168).
